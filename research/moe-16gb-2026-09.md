# MoE vs dense text models for the fleet — is MoE faster? (2026-09)

Date: 2026-09-26. Status: **research only — nothing adopted or qualified.** Owner direction
recorded in [`research/moe-fleet-qualification-handoff.md`](moe-fleet-qualification-handoff.md)
(Granite 4.0 H-Tiny 4-bit MLX for 8 GB, LFM2.5-8B-A1B 4-bit MLX for 16 GB, dense Qwen3.5-9B
4-bit kept for scripts) — a qualification plan, not an adopted decision. Evidence class is
labelled per claim: **[M]** measured, **[V]** vendor claim, **[I]** inference.
Every model is named with its quantization. Fleet per `research/owner-hardware.md`.

## The question

The current common model, **Qwen3.5-9B 4-bit** (dense), runs but is slow: owner-measured
**12 tok/s on M1, 14 on M2, 18 on M4 16 GB** [M, owner 2026-09-26]. Would a **Mixture-of-Experts
(MoE)** model be faster?

## Short answer

**Yes — but only inside the same memory budget, and on 16 GB that means the *small* MoEs, not the
famous 30B-A3B ones.**

MoE does not reduce *memory*: for single-device inference every expert stays resident, so peak RAM
tracks **total** parameters. What it reduces is **bytes read and FLOPs per generated token**,
because only the **active** experts run. Speed therefore scales with *active* params, while
**fit still scales with total params**. On a 16 GB Mac the binding constraint is total size, so a
35B-A3B model is simultaneously "fast per token" and "will not fit."

## Why the dense 9B is slow on a base chip

A dense 9B 4-bit model reads almost all ~6 GB of weights for every token. Base M1/M2/M4 have
memory bandwidth roughly an order of magnitude below a Max/Ultra part, which is exactly the
12–18 tok/s the owner sees [M, owner]. A 1–1.5B-active MoE reads only ~0.7–1.2 GB per token
[I], so the same machine should generate several times faster — the win is real, but it is a
function of *active* params, not of the "MoE" label.

## The fit trap — the fast MoEs that do **not** fit 16 GB

On-disk MLX sizes verified from the HF API on 2026-09-26 [M]:

| Model (quantization) | Total / active | On-disk | Fits 16 GB? |
| --- | --- | ---: | --- |
| `mlx-community/Qwen3-30B-A3B-4bit` | 30.5B / 3.3B | **17.19 GB** | **No** — 24 GB tier (2 machines) |
| `mlx-community/gemma-4-26B-A4B-it-qat-4bit` | 26B / 4B | **15.64 GB** | **No** — weights alone leave no room on 16 GB; 24 GB [M, measured on M4] |
| `Qwen3.5/3.6-35B-A3B` 4-bit | 35B / 3B | ~20.4 GB | No — 32 GB (1 machine) |
| `openai/gpt-oss-20b` MXFP4 | 21B / 3.6B | 11.18 GB | Yes, but **not for this workload**: last of 21 on strict JSON (SOB 0.845) and near-bottom on creative writing (#130/133) [M] |

So the MoE class people usually mean is a **24/32 GB** answer, not a 16 GB one.

`qwen3_moe.py` [M, inspected in the installed runtime]. Both LFM2.5 and Granite 4.0 H-Tiny are

of their long-context efficiency comes from.

## Measured Apple-Silicon throughput (not one of the owner's machines — labels matter)

Community **oMLX** benchmarks [M]:

| Model | Machine | Quant | Decode |
| --- | --- | --- | --- |
| LFM2.5-8B-A1B | M1 Max 32c, 64 GB | bf16 | **69.5 tok/s @1k → 66.9 @8k → 59.2 @32k → 37.6 @128k**; peak 16.2 → 19.0 GB |
| granite-4.0-h-tiny | M5 Max 40c, 128 GB | 8-bit | **169.6 tok/s @1k → 144.4 @8k → 88.2 @128k**; peak 11.2 → 13.3 GB |

Those are Max-class chips with far more bandwidth than the fleet's base M1/M2/M4, and the LFM2.5
run is bf16 (peak 16–19 GB — **not** a 16 GB fit at bf16). The 4-bit builds above are the 16 GB
forms. Directionally: a 1–1.5B-active MoE decodes roughly **3–4× faster than the dense 9B at
equal-or-better memory**, which is what the architecture predicts [I].

**Reconcile before trusting either baseline:** a dev-machine run on this repo's M2 Max 34 GB
measured only ~2.9 tok/s for Qwen3.5-9B 4-bit, far below the owner's 14 tok/s on a plain M2 and
unexpected for an M2 Max; that run had the model's thinking trace enabled and the checkpoint loads
as a VL architecture, so it is not a clean like-for-like number [M, flagged].

## Quality — the real trade

- **LFM2.5-8B-A1B 4-bit** is the strongest small-MoE candidate: instruction-following and
  structured-output numbers well above Granite H-Tiny and near a dense 9B, and it is explicitly
  positioned for **structured outputs, tool use and on-device assistants** [V]. It is a
  **reasoning model** — it emits an explicit chain of thought, so the app must suppress or budget
  that exactly as it must for Qwen3.5's `Thinking Process` trace [V].
- **Granite 4.0 H-Tiny 4-bit** is the smallest/fastest and has the longest pedigree for document
  and JSON extraction, but its **creative-writing score is weak (32.60)** [V], which matters for
  long-form narration.
- **Qwen3-4B-Instruct-2507 4-bit** is the dark horse: dense, only **2.28 GB**, faster than the 9B,
  and its creative-writing signal (51.71) is *better than LFM2-8B-A1B's 44.22* in the same vendor
  table [V]. If prose quality is the constraint, this may beat the small MoEs.
- **Prose at 1–1.5B active is the open risk.** No independent long-form narration evaluation was
  found for LFM2.5-8B-A1B or Granite 4.0 H-Tiny 4-bit. The dense Qwen3.5-9B 4-bit remains the
  known-prose model; MoE is the *speed* bet, not yet a quality-proven one.

## Prose and JSON are different problems — weigh them separately

**JSON is an engine property, not a model property.** Grammar/schema-constrained decoding
(llama.cpp GBNF or a JSON schema) makes validity ~100% and is largely model-agnostic. The same
checkpoint in MLX and GGUF is the same weights and the same quality — GGUF is chosen for the JSON
lane only because llama.cpp can constrain decoding and the plain `mlx-lm` server cannot. Both
candidate MoEs are supported by llama.cpp — **LFM2-MoE hybrid**
([PR #16464](https://github.com/ggml-org/llama.cpp/pull/16464)) and **Granite hybrid**
(`LLM_ARCH_GRANITE_HYBRID`, `"granitehybrid"`) — so the outline arrays, structured image prompts
and metadata extraction can run on the fast MoE through **GGUF + grammar** with JSON risk off the
table. Native, unconstrained generation never reaches 100% (best measured Structured Output
Benchmark pass 0.987 [M]); the grammar is the fix, not a bigger model.

**Prose is a model property, and length is the stress test.** POLARIS
([arXiv 2606.04095](https://arxiv.org/abs/2606.04095), EMNLP 2026) trains **Qwen3.5-9B** and opens
with the finding that small open-weight models *"either fall far short of the requested length, or
their quality significantly degrades as length increases … length generalization is a meaningful
stress test."* Creative-Writing-v3 signals for the candidates [V, Liquid AI comparison table]:
Gemma-3-4b-it **68.56**, Qwen3-4B-Instruct-2507 **51.71**, LFM2-8B-A1B **44.22**,
Granite-4.0-H-Tiny **32.60**. The small MoEs are the *weakest* prose options, and Granite H-Tiny
is explicitly a structured-extraction model, not a writer.

**Map each artifact you actually write to the axis that decides it:**

| Artifact | Shape | What decides quality |
| --- | --- | --- |
| Image prompts | descriptive, often JSON-ish | **grammar + speed** — a fast MoE is fine |
| Outline | JSON array | **grammar** — a fast MoE is fine |
| Metadata (title/description/tags) | short prose | **speed** — a fast MoE is fine |
| Script / narration | long-form prose | **model quality + length adherence** — keep the dense 9B |

`rishanthrajendhran/POLARIS-9B` is that same dense 9B fine-tuned with GRPO to write long stories
much better (competitive with Qwen3.5-27B per its blinded evaluation), but it is **gated**
(HF access approval required), **18.84 GB** bf16, with **no MLX quant found** — not a drop-in. It
does show the prose lever is *training*, not architecture.

## Recommendation — what to qualify, in order

The "one model across the fleet" rule is about not keeping a different model **per machine**; it
does not require one model for every **artifact**. Given prose and JSON pull in opposite
directions, qualify a two-lane setup and only collapse it if one model passes both:

1. **Speed + JSON lane** for image prompts, outline and metadata:
   **`LiquidAI/LFM2.5-8B-A1B-MLX-4bit` (4.85 GB)** at 16 GB, or
   **`mlx-community/granite-4.0-h-tiny-4bit` (3.92 GB)** where 8 GB fit matters — both served
   through **GGUF + JSON-schema grammar** for the `JSON.parse` sites.
2. **Prose lane** for the script: keep **Qwen3.5-9B 4-bit** (dense, known prose). Do not move the
   script to a 1–1.5B-active MoE without a measured long-form comparison — that is exactly where
   POLARIS says small models fail.
3. **Dense control to try**: **`mlx-community/Qwen3-4B-Instruct-2507-4bit` (2.28 GB)** — faster
   than the 9B, and a *better* creative-writing signal than either small MoE (51.71 vs 44.22 /
   32.60). If it holds up on a real chapter, it may beat the MoE for a single model.
4. Keep **Qwen3.5-9B 4-bit** as the prose model and **Gemma 4 26B-A4B QAT 4-bit** /
   **Qwen3-30B-A3B 4-bit** as the 24 GB fallback for the two M4-24 machines.

If one model for everything is non-negotiable, the test is: give **LFM2.5-8B-A1B 4-bit** a full
long-form chapter prompt and judge **length adherence and quality at 8–12k characters** against
the dense 9B. If it degrades, it is a drafting and prompts model, not the script model.

Run every candidate on the **real artifacts** — outline (JSON), one chapter (prose), thumbnail
prompt set (JSON), metadata — and record tok/s, peak memory, **JSON validity** and a prose
verdict per machine. Do not choose on MMLU alone.

## Caveats

- MoE **speed is not free of routing overhead**; the real speedup is measured, not the 4× the
  parameter ratio suggests.
- Hybrid Mamba/MoE decode has known slow kernels in some runtimes (e.g. `mlxcel` issue #1685
  reports `GraniteMoeHybrid` at ~⅓ of `mlx-lm` speed) — throughput is runtime-dependent.
- Both LFM2.5 and Qwen3.5 emit reasoning traces by default; a thinking toggle is required either
  way.
- Quantization changes quality; the 3-bit tiers are for 8 GB fit, not for fidelity.
