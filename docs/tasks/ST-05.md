## Handoff — packaged end-to-end probe, 2026-09-15 (round 18)

The heavy models were probed through the packaged app with the fixed resolver, using a locally
staged reference clip. Evidence: `qualification/evidence/st05-heavy-voices-e2e.json`.

| Model | Result |
| --- | --- |
| `mlx-community/OmniVoice-bfloat16` | **DONE** — 197,804 bytes, sha256 `c5683385…`, 21.9 s |
| `mlx-community/VoxCPM2-4bit` | error: "voxcpm-mlx produced no audio … host has 17.2 GB unified memory, 6.1 GB free … usually the request being too large for the available memory" |
| `mlx-community/VoxCPM2-bf16` | same memory error (4.6 GB free at the time) |
| `mlx-community/VoxCPM2-8bit` | still `queued` when the probe window closed — not attempted to completion |

**Interpretation — this is a host-memory result, not a code defect.** All four packages are
`files_verified` after `/verify` and all four were accepted for dispatch; OmniVoice produced real
audio on this 16 GiB machine. The VoxCPM2 variants failed with the model's own explicit
memory-shortfall message while three engines (Voice + Image + Subtitle) were resident. The owner
has M4-24 and M2 Max-32 machines, and stated that model-fit checking is their call, so the correct
next step is to **re-run the VoxCPM2 probe on a larger machine with the other engines idle**, not to
change code. VoxCPM2-8bit should be re-probed rather than inferred from the 4-bit result.

Outstanding for ST-05: VoxCPM2 receipts on suitable hardware, capability/UI exposure in the app
(the Audio form currently targets the Qwen family), cancellation/restart receipts, and independent
review.
