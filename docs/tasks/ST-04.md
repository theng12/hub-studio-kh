## Packaged end-to-end clone test (round 9) — reference contract works, dispatch blocked

The native clone path was exercised against the packaged app through the Hub API, matching what
`1a010e5` sends.

**What works.** The reference stage is correct: `POST /api/hub/voice-references` with the clip,
its transcript, language and `sha256` returned **201**, `origin: "local"`,
`transcript_supplied: true`, and the returned `asset_id` was accepted as a top-level
`voice_reference_asset_id` on `POST /api/hub/jobs` (submit 200, no `VOICE_REFERENCE_CONFLICT`,
no ingress error). So the Hub envelope lift from `4939329` does what the native client needs.

**What blocks.** The clone job then stays `queued` with an explicit governor note:

> `'mlx-community/Qwen3-TTS-12Hz-0.6B-Base-8bit' not downloaded on voice — broadcast the download or try another machine`

That string comes from `components/hub/backend/broker.py:2205-2207`, which refuses dispatch when
`not entry.get("is_cloud") and not is_cached(entry)` — i.e. **the Voice worker's own catalog row
for the Base model does not report it as cached.** Meanwhile the Hub's model-package view for the
same package reports `files_verified` / `dispatch_state: eligible` after a `/verify` call. Note
also that both Base packages read `invalid` **before** `/verify` and only become verified after it,
consistent with the `ctime`-sensitive stamp.

So there are two vocabularies again, this time between "a verified ST-01 package in the model
library" and "a model this worker considers downloaded". The ST-04 real-model proof succeeded
because it built an HF-cache library by hard-linking the verified files, which is exactly the
layout the worker looks for.

**Next diagnostic (cheap, decisive):** print the Base row from
`GET /studio/voice/api/generate/availability` and read its `cache.state` / `cached` fields, then
compare that against how the worker decides `is_cached` for CustomVoice (which does dispatch).
Then decide whether the fix is (a) making the worker's cache detection recognise the ST-01 package
layout, or (b) having the package import/verify flow materialise the cache entry the worker
expects. Either way the user-facing contract must stay "a verified package is usable", otherwise
the app will tell the owner a model is installed and then refuse to use it.

## Round 10 — the blocker is not Base-specific: the Voice worker sees NO model library

Reading the actual values settles it. In the packaged app started with `--models-dir model-library`
(the ST-01 verified package library), the aggregate catalog reports for **every** Qwen entry —
Base *and* CustomVoice:

```
{"repo": "mlx-community/Qwen3-TTS-12Hz-0.6B-Base-8bit", "hub_cached": false,
 "cache": {"state": "absent", "snapshot_revision": null, "path": null,
           "bytes_complete": 0, "bytes_incomplete": 0}}
```
and identically for `…0.6B-CustomVoice-8bit`, `…1.7B-Base-8bit` and `…1.7B-CustomVoice-8bit`.

So the Voice worker's cache detector resolves **nothing** in the ST-01 package layout. That makes
the broker's gate (`monitor.is_cached` requires `cache.state == "cached"`, used at
`broker.py:2205`) refuse **every** Voice dispatch — not only the new Base models. The earlier
CustomVoice success came from a proof that used an HF-cache-shaped library, which is the shape the
worker is looking for; `cache` publishes `snapshot_revision`/`path`, so the worker has a snapshot
resolver that does not understand `<library>/<package>/<revision>/…`.

Image is not affected: ST-03 produced a real image in the packaged app from this same library, so
the Image worker does resolve the package layout. **This is a Voice-specific integration gap and a
user-facing one** — the app would tell the owner a model is installed and verified, then refuse to
generate with it.

**Next step:** find the Voice worker's cache/snapshot resolver (it is what populates `cache.state`,
`path` and `snapshot_revision`; it is not in `catalog.py`) and make it resolve the verified package
folder the same way the Image worker does, or have the package import/verify flow materialise the
snapshot the Voice worker expects. Whichever is chosen, "verified package" and "downloaded" must
mean the same thing to every studio.

## Round 11 — the resolver is found: HF-cache only

`components/voice/app/backend/cache.py` is the resolver behind those `absent` rows:

- `hub_dir()` (line 37) → `hf_home() / "hub"`; `repo_cache_dir(repo)` (line 41) →
  `<hf_home>/hub/models--org--name`; `snapshot_revision(repo)` (line 47) reads
  `…/refs/main` plus the snapshot folders.
- `status_snapshot(repo)` (line 347) builds exactly the dict the Hub surfaces, and returns
  `"path": None` and `state` `absent` unless an **Hugging Face cache** entry exists.

So the Voice worker only ever looks in an HF cache directory. The app's library is
`<models-dir>/<package_id>/<revision>/…` (the ST-01 verified-package layout, which the Image
worker does read — that is why ST-03 generated a real image from this same library). Nothing
bridges the two, which is why every Qwen model reads `absent`.

**Fix to implement and then verify end to end:** teach the Voice cache resolver to answer from the
verified package library when the repo is present there — i.e. return `state: "cached"`,
`path: <package folder>` and `snapshot_revision: <revision>` for a package in `--models-dir` whose
receipt verifies, and keep the existing HF-cache behaviour as the fallback. The model packages
already carry `model_id` and `revision` (see `model-manifests/*.json`), and
`components/model_packages.py` already exposes preflight/verification, so the bridge is small.
Two constraints: only a **verified** package may count as cached (never a partial or invalid one),
and the working-directory/library path must come from the worker's `--models-dir` rather than a
new global.

**Not yet done:** the code change itself, and the packaged end-to-end clone proof after it. This
round deliberately stopped at locating the resolver rather than shipping an untested change.

## Round 12 — the bridge is small but has two sharp edges; recorded rather than guessed

`hf_home()` (`cache.py:23-34`) already prefers `STUDIOHUB_MODELS_DIR`, and the packaged Hub sets
that to the model library — so `hf_home()` **is** the app's library and the bridge is local, not a
new global. The package index is `<library>/.studiohub/installed.json`, keyed by `package_id`,
with rows of `{revision, manifest_sha256, folder, files}`.

Two things must be settled before writing it, and both are cheap to check:

1. **The index has no `model_id`.** It maps `package_id → folder/revision`, but the Voice cache
   functions are called with a **repo**. So the bridge needs a repo→package mapping, which lives in
   `model-manifests/*.json` (`model_id` and `revision` per package). Confirm the worker can reach
   those manifests — the Hub sets `STUDIOHUB_MODEL_MANIFESTS` for **itself**, while the workers are
   spawned with a minimal environment (`env={'PATH': …, 'LANG': …}` in `hub_worker.py`), so a
   worker that needs the manifest directory must receive it explicitly (argument or its own env
   entry) rather than assuming the variable is inherited.
2. **Only a verified package may answer "cached".** The index stores a stamp per file including
   `st_ctime_ns`, which is exactly what made `/verify` necessary earlier. The bridge must not
   report a package as cached merely because a folder exists; it should require the same verified
   state the Hub's model-package view reports, otherwise a broken model would be dispatched.

Both are one-line checks; making them first avoids shipping a bridge that reports models as
available when they are not — the inverse of the bug being fixed.

**Status: the change is scoped and the two preconditions are named, but no code was written this
round.** Verification requires staging the app (~2 min) plus a real clone generation, so this is
the first task of the next round rather than a half-tested patch now.

## Round 15 — exact cause: the package splits weights from the tokenizer

The full traceback from the packaged run settles it. The model **loads successfully**; the
failure is at inference setup:

```
mlx_audio/stt/models/whisper/decoding.py:97  get_suppress_tokens → tokenizer.non_speech_tokens
mlx_audio/stt/models/whisper/whisper.py:176  result = {self.encode(" -")[0], self.encode(" '")[0]}
IndexError: list index out of range
```

`self.encode(" -")` returns an **empty list**, i.e. the Whisper tokenizer is not loaded. The
reason is the package layout: a Studio Hub package keeps weights and config in
`<revision>/model/` (`config.json`, `weights.safetensors`) and the tokenizer/processor in
`<revision>/companions/processor/`. mlx_audio expects the Hugging Face snapshot layout, where the
processor files sit **beside** the weights, and `WhisperProcessor.from_pretrained(model_path)`
finds nothing when handed `<revision>/model` alone. So the weights load and the tokenizer silently
falls back to an empty/dummy one.

**Recommended fix (small, and it does not touch the library):** when resolving a package
snapshot, build a merged read-only view once — a directory (under the app's data dir, never inside
the model library) containing symlinks to `<revision>/model/*` plus the files from
`<revision>/companions/processor/` — and hand that to mlx_audio. The Subtitle engine already reads
this same package successfully, so its loader is the reference for exactly which companion files
must be present; check there rather than guessing. The alternative, reshaping the library itself,
would modify verified bytes and should be avoided.

**Why this matters beyond Voice:** the same split-layout assumption is what made Base/Small
"catalog-only" earlier (`weights.npz`), so one adapter that materialises a correct snapshot view
would likely fix Whisper loading for every consumer.

**Status:** cause proven; the adapter is written up but **not implemented or verified**. The
packaged clone reaches the reference quality check and does real work before this point.

## Round 16 (cont.) — ROOT CAUSE FOUND: the tokenizer fallback asks the hub by name, offline

The hypothesis above was wrong; the real cause is one call.

Two facts together explain everything:

1. mlx_audio loads the processor from the model path and **swallows the failure into a warning**
   (`whisper.py:698-704`, confirmed present in the packaged worker log), leaving
   `model._processor = None`.
2. The Voice code anticipates exactly this and calls `self._attach_processor(model, repo)`
   (`transcription.py:723-730`) — but that helper loads the tokenizer from the **base OpenAI repo
   by name**: `WhisperTokenizer.from_pretrained("openai/whisper-large-v3-turbo")`
   (`transcription.py:756-760`, `_PROCESSOR_BASE`). In an offline packaged app with no HF cache
   entry for that repo this cannot succeed, so no tokenizer is attached — and decoding later dies
   at `whisper.py:176  self.encode(" -")[0]` with an empty list.

Crucially, **the app already ships those tokenizer files**: ST-01 imported the OpenAI tokenizer
into the package as `companions/processor/` (seven files — `tokenizer.json`, `vocab.json`,
`merges.txt`, `tokenizer_config.json`, `special_tokens_map.json`, `normalizer.json`,
`added_tokens.json`), and the merged view now places them beside the weights. The fallback simply
never looks there.

**The fix (small, one place):** in `_attach_processor`, try the **local** processor directory first —
`WhisperTokenizer.from_pretrained(<local companion/processor dir>)` (the merged view or
`<revision>/companions/processor`) — and only fall back to the `openai/…` hub name when no local
copy exists. That keeps offline installs working, uses files the app already verified, and removes
the last dependency on the network in the Voice path.

**This is the last link.** Everything upstream is verified in the packaged app: the Hub gate, the
model resolution, the weights load, the reference stage/validate, and the snapshot view. Note this
same fallback is why the Subtitle engine works where Voice did not — Subtitle's engine reads the
companion files directly rather than asking the hub by name.

**Not implemented or verified this round.** The change and the end-to-end clone proof are the next
task, and they are now a single, precisely identified edit.

## Coordinator findings from this integration

- **Native client mismatch, fixed on the Hub side.** `HubAudioRequest` sends `voice_reference_asset_id` at the top level of the job envelope, but the Broker read it only from `sharedParams`/item params, so every native Base job would have failed. `4939329` adds a lift (`_shared_params_with_local_reference`); an explicit `sharedParams` value still wins. No native change was required.
- **`requiresReference` is now catalog-driven** (`04dc134`): the Voice catalog publishes `reference_audio.{declared,supported,transcript}` and the Audio UI derives clone-vs-preset and transcript requirement from that, with the model-name heuristic only as a fallback.
- **Keep shipping `components/voice/model-audits`.** The Base reference contract is audit-bound and refuses a clip without it (`REFERENCE_AUDIO_CONTRACT_UNAVAILABLE`).
- **Model-library verification is `ctime`-sensitive.** `components/model_packages._stamp()` includes `st_ctime_ns`, so hard-linking library files (which the ST-04 proof harness does to build an offline cache) changes the stamp and the app reports `File changed; verify again` even though the bytes are identical. Verified directly: `whisper-turbo/.../companions/processor/added_tokens.json` hashes to the recorded value but now carries 4 hard links. Remedy for the owner is a **Verify** pass; the harness should copy rather than hard-link, and whether `ctime` should count as tampering is a design question for ST-11.

Do not mark DONE with unchecked requirements. Partial model/hardware checkpoints remain visible.
