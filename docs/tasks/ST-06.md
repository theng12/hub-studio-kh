## End-to-end verification through the packaged app (2026-09-15) — one fix landed, one blocker open

The native screen and packaging integration were tested for real: a staged app was launched, Whisper Turbo verified, and a real ~5 s WAV submitted through `POST /api/hub/transcription/jobs`.

**Fixed (release-blocking):** every Subtitle job stayed `queued` forever with
`governor_note: "model is not available for this job modality"`. `create_batch`'s submit-time
admission guard runs on the request envelope (which carries `modality: "transcription"`), so
submission returned 200 — but the **persisted batch dict had no `modality` at all**, and
dispatch re-runs the same guard on the stored batch, so the packaged engine→modality check
(`subtitle-mlx` → `transcription`) could never match. Fixed in `bc0119b` by persisting the
modality on the batch.

**Still open after that fix:** the job now passes admission (`governor_note: null`) but still
never dispatches — it sits `queued` with no error, no governor note and no studio assigned.
Verified healthy at the same moment, so these are **not** the cause: the `subtitle` worker is
registered with `modality: transcription`, `local: true`; `/studio/subtitle/api/transcribe/availability`
returns `available: true` with turbo `cached: true, ready: true`; `/api/health` reports
`{ok: true, workers: 3}`; the model manifest maps `subtitle-mlx` → `transcription`; and
`/api/hub/model-packages/whisper-turbo` is `files_verified` / `dispatch_state: eligible`.

The refusal is therefore in one of the **silent** gates inside
`transcription_jobs.dispatch_once` → `_eligible_studios` → `broker.prepare_machine_memory`.
The two candidates, in order of likelihood:

1. `_memory_gate(...)` inside `broker.prepare_machine_memory` returning something other than
   `run` (16 GiB host with Voice + Image + Subtitle workers resident). This path records only
   `broker.note_external_memory_block(...)`, never `governor_note`, so it fails silently.
2. One of the `_eligible_studios` conditions — `monitor.status[studio]["status"] == "up"`,
   `machine in broker.busy_machines()`, `broker.in_maintenance("subtitle")`,
   `machine_is_quarantined("local")`, or `studio_enabled("local", "subtitle")`.

**Next step:** surface the real reason — either log the `prepare_machine_memory` note, or expose
the transcription governor's current refusal through an API — then fix accordingly. A
silent infinite `queued` with a healthy worker is the worst diagnostic outcome; whichever gate it
is, it must become visible. This is the single remaining item before a real Subtitle job can be
proven end to end, and it is also why the ST-06 claim of "Turbo works" is currently scoped to the
worker and fixture boundary, not the packaged app.

### Round 7 update — two blockers fixed, one precise blocker left

**Fixed (a): silent gate instrumented.** `dispatch_once` now records the real reason into
`governor_note` — either the per-studio rejection reasons from `_eligible_studios` (which gained
an optional `reasons` collector) or the memory-admission decision. That immediately produced the
next root cause instead of another silent queue.

**Fixed (b): the Subtitle worker was never even considered.** `monitor.py` refreshed Whisper
availability only for studios whose modality is `"voice"`. The standalone Subtitle worker's
modality is `"transcription"`, so its transcription cache was **never populated**; the
cache-only scheduling view always returned `None` and reported "reports transcription
unavailable" while the read route happily returned `available: true`. Added
`reports_transcription()` and applied it at all four filter sites so the aggregate pairing stays
consistent. **Result: the job now dispatches — `status: running`, `studio: subtitle`.**

**Remaining blocker (precise and small).** The dispatch now reaches the worker, which answers
`422 choose one of the packaged Whisper models`. Cause: `transcription_jobs._run_item` sends
`"model": batch["model"]`, i.e. the Hugging Face **repo**
(`mlx-community/whisper-large-v3-turbo`), while
`components/subtitle/app/backend/manager.py:validate_request` requires the value to be in its
`packages` list, i.e. the **package id** (`whisper-turbo`). The two vocabularies disagree.

Fix options, to be chosen deliberately: (1) have the worker accept the repo as an alias for its
package (the worker's own catalog already publishes both `repo` and `package_id`, and the
availability route keys `default_model` on the package id, so accepting both is the smallest
honest change); or (2) have the Hub translate repo → package id at dispatch, using the manifest
catalog it already loads. Option 1 keeps the Hub's existing transcription contract intact, which
the retained Voice endpoint also used.

### Round 8 update — Subtitle works end to end in the packaged app

Option 1 was applied (`418da53`): `validate_request` resolves an optional alias map built from
the real manifests, so both the repository and the package id are accepted and an unpackaged
model is still refused. Four pinning tests were added, including one asserting the alias map is
derived from the manifests rather than hard-coded.

**Real packaged proof:** audio submitted through the packaged app was transcribed by the
