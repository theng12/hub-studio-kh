## 1. Verdict

**No — ST-14.8 is not passable as it stands.**

Two things have to be separated, because they point in different directions:

- **The HTTP-level claims are real.** I independently reproduced the central measurements —
  262,144 context, a real completion with no thinking trace, JSON mode `json_valid: true` with 0
  repairs, and `active_memory_bytes` to the byte. The model manifest is exact: all eleven files
  hash-match on disk, 5,977,071,067 bytes. The engine's thinking default is genuinely off, proven
  against the *real* tokenizer. This is not a fabricated qualification.
- **The product is not reachable end-to-end**, which is what ST-14 asked to prove. The released
  build (`9ef3ac6` → 0.6.57) answered **HTTP 500** on `/api/hub/model-packages` and the native app
  read that as "the Hub is not answering" — every model picker empty (F1, since hotfixed). On this
  Mac the chat model also has **no install receipt**, so the Chat page's Send button is disabled
  by the app's own gates (F2), the model picker's value is never sent (F3), a cancelled streaming
  request wedges the worker's model lock indefinitely (F4), and an abandoned request reserves the
  whole Mac for six hours (F5). None of the four are covered by any test or by the evidence note.

Taking the current tree rather than the reviewed one, F1 is closed and F2/F4/F5 remain. That is
still a **no**: the Chat Studio cannot be used from the app that ships it, and two ordinary
failure modes leave the worker or the machine stuck.

## 2. Findings, most serious first

### F1 — `GET /api/hub/model-packages` returned HTTP 500 with the shipped catalog, which disabled every model picker **[M]** — *fixed at `eea477e`*

- **What.** `_model_state` mapped a manifest's engine to its worker with an inline dict that
  listed `image-mflux, voice-mlx, voice-vits, subtitle-mlx, music-mlx`. `components/model_packages.py:57`
  had been taught `chat-mlx`, and `model-manifests/qwen3-5-9b-4bit.json` had been added to the
  release catalog — so the lookup raised `KeyError: 'chat-mlx'` inside the route.
- **Where.** `components/hub/standalone.py:74-75` (reviewed revision). The route catches only
  `ValueError` (`standalone.py:640-647`), so the `KeyError` became a 500. The catalog is loaded
  from `resources/model-manifests/*.json` (`standalone.py:42-52`, staged by
  `packaging/stage_voice.py:252`), so this fired on every install **whether or not the chat model
  was downloaded**.
- **How established.** `standalone._model_state(chat_manifest, real_catalog, stub_monitor)` raised
  `KeyError: 'chat-mlx'`; then, with `STUDIOHUB_MODELS_DIR=$HOME/StudioHubModels` and the real
  `model-manifests/` tree,
  `TestClient(standalone.create_app(start_background=False)).get('/api/hub/model-packages')`
  → **500 "Internal Server Error"**. The installed bundle at the time carried the same manifest
  list (`/Applications/Studio Hub.app/Contents/Resources/model-manifests/qwen3-5-9b-4bit.json`).
- **What breaks.** `native/StudioAPI.swift:1404` fetches that route inside `refresh()` with a hard
  `try` (deliberately not `try?`, with a comment saying these two are "the Hub itself"), and the
  catch sets `isReachable = false`. So one 500 did not degrade one list: the whole refresh threw,
  every model picker went empty, and the Hub was reported as not answering. The chat evidence
  never saw it because `POST /api/hub/chat/completions` does not touch `_model_state`, and every
  Hub test of that route points `STUDIOHUB_MODEL_MANIFESTS` at fixture manifests that contain no
  chat row.
- **Smallest fix.** Add `"chat-mlx": "chat"` to the map. *Done upstream of this review*, as
  `_worker_for_engine()` (`standalone.py:71-95` at `eea477e`), with a new test that walks the real
  catalog. I re-ran it: `/api/hub/model-packages` → **200**, 20 packages, chat row present with
  `worker_id: "chat"`, and `tests/test_model_manifest_catalog.py` 12 passed (20 subtests). The
  hotfix is the right shape — a named mapping plus a drift guard — and I could not find a
  remaining path that reaches an unmapped engine.

### F4 — A streaming request that loses its client wedges the worker's model lock indefinitely **[M]**

- **What.** `ChatEngine.stream()` holds `self._lock` for the whole generator
  (`components/chat/app/backend/llm_engine.py:321-342`); `complete()` takes the same lock
  (`llm_engine.py:276`). When a client disconnects mid-SSE, Starlette cancels the response task
  but never closes the sync generator, so its `finally` — which resets `_generating` and drops
  the lock — does not run. The generation itself is also not stopped.
- **Where.** `components/chat/app/backend/llm_engine.py:321-342` (lock held across yields),
  `components/chat/app/backend/main.py:181-210` (`StreamingResponse(events())` over a sync
  generator).
- **How established.** A real uvicorn server running the real `create_app` with an engine double
  that mirrors the lock; a raw-socket client sent `{"stream": true}`, read the first SSE chunk,
  then closed the socket. Result: the generator was still suspended **120 s later**
  (`finished=0`, `chunks=1` of 60 — the full stream would have taken 6 s) and
  `lock.locked() == True`. The same shape happened at 30 s. A later unrelated request appeared to
  let CPython finalise the abandoned generator, i.e. recovery depends on GC, not on the
  disconnect.
- **What breaks.** Every later `complete()` blocks on the lock forever — and because FastAPI runs
  sync endpoints in a threadpool (anyio's default limit is 40), repeating streaming requests
  exhaust the worker's threads until even `/api/health` stops answering, at which point the Hub
  marks the studio down. The memory-policy idle thread also blocks inside `release()`
  (`memory_policy.py:103-113` → `engine.release` → `with self._lock`), so idle release stops
  working permanently. **Reachability:** the Hub forwards any client body verbatim and its own
  proxy drops the upstream connection if *its* caller vanishes, so a `stream: true` request
  abandoned at the native/API layer is enough. Nothing in the app sends `stream: true` today, so
  this is a live hazard rather than a daily failure — but nothing prevents it either, and the
  worker's SSE route is advertised (`research/chat-studio-adoption-2026-09-24.md` calls streaming
  a supported feature).
- **Smallest fix.** Bound the streaming path the way the non-streaming one is bounded: wrap the
  generator body in `try/finally` **inside the endpoint** (not only inside the engine) and release
  the lock there, or run the stream through a cancellation-aware iterator
  (`anyio`-friendly) that closes the generator when the client goes away. Upstream of that, a
  cheap mitigation is to refuse `stream: true` at the Hub route until the worker can cancel.

### F5 — An abandoned chat request reserves the whole Mac for six hours **[M]**

- **What.** `/api/hub/chat/completions` goes through the peer-proxy path, which takes an
  *external machine lease* for the local machine. The lease is released only in the
  `except (httpx.HTTPError, OSError)` handler and in `_settle_peer_lease`. `asyncio.CancelledError`
  is a `BaseException`, so a client disconnect (which cancels the ASGI task) skips both.
- **Where.** `components/hub/standalone.py:1633-1682` (`studio_proxy`), `:265-271`
  (`_reserve_peer_machine`), `:218` (`_PEER_LEASE_TTL_S = 6 * 3600.0`), `:1684-1691`
  (`hub_chat_completions`), `:332-344` (`_peer_work_request` returns True for
  `v1/chat/completions`).
- **How established.** Same harness as F1: a stub chat worker that sleeps, a real
  `/api/hub/chat/completions` POST, the client task cancelled mid-flight. Output:
  `leases AFTER cancel: {'peer:chat:ee90641a…': ('local', …)}`,
  `busy machines AFTER cancel: ['local']`, and the **next** chat request →
  `409 {"detail":"local is reserved for other work on this Mac","code":"MACHINE_BUSY"}`.
  `busy_machines()` includes `_external_machine_leases` (`components/hub/backend/broker.py:1210-1217`),
  so the local admission paths refuse too.
- **What breaks.** Quitting the app, closing the window, or a dropped connection during a
  generation leaves the Mac reserved for up to six hours: chat itself answers 409, and image /
  voice / music dispatch on that machine is refused with `MACHINE_BUSY`. The 60-second prune
  (`:249-262`) only removes *expired* leases, so it does not help.
- **Smallest fix.** Release the lease in a `finally` rather than in the `except`, e.g. take the
  upstream call into `try: … finally: if owner is not None and response is None: _release_peer_lease(owner)`,
  or widen the handler to `except BaseException` and re-raise. Add a test that cancels the proxy
  task and asserts `_PEER_LEASES` is empty. (The same `finally` also covers the unhandled-error
  case, which leaks identically.)

### F6 — The fleet/peer surface cannot carry chat, and the docs say it can **[M]**

- **What.** `fleet_path_allowed` is a closed allowlist and `_FLEET_STUDIO` is
  `(?:voice|subtitle|image|transcription|music)` — no `chat`. So a Fleet-token holder gets **403**
  on both `/api/hub/chat/completions` and `/studio/chat/…`, including `/studio/chat/v1/chat/completions`,
  which `_peer_work_request` explicitly classifies as new work.
- **Where.** `components/hub/backend/auth.py:413` and the `FLEET_ALLOWED` rows at `:430-455`;
  `components/hub/standalone.py:332-344` (dead predicate branch);
  `docs/tasks/HANDOFF.md:208` ("the `/studio/chat/...` peer proxy" listed as delivered wiring).
- **How established.** ASGI probe with a non-loopback client and a stubbed fleet token:
  hub token → reaches the worker (502 against a dead port), fleet token →
  `403 "The fleet credential may send work to this Mac …"` on both chat paths; and
  `auth.fleet_path_allowed("POST", "/studio/chat/v1/chat/completions")` → `False` while
  `("GET", "/studio/image/api/catalog")` → `True`. (A loopback client with
  `STUDIOHUB_REQUIRE_AUTH` unset is unauthenticated by design; `packaging/hub_worker.py:219`
  sets that variable to `1` for the packaged Hub, so in the app the Hub token is required.)
- **What breaks.** Nothing today — chat is deliberately local-only — but the wiring is
  inconsistent with itself and with the handoff: the route that was added to make chat
  *dispatchable* to a peer is unreachable for every credential that dispatches, and
  `_peer_work_request`'s chat branch is dead code. Anyone reading HANDOFF would assume a
  controller can drive a node's chat. Either add chat to the allowlist (if that is intended) or
  say plainly in the card/handoff that the peer surface is closed to chat until the fleet story
  is decided. Free the dead predicate branch either way.
- **RESOLVED 2026-09-25, in 0.6.63 — and the finding above is kept as written.** The owner chose
  the first option, and stated the principle behind it: *"all models and generators should be
  shown and runnable… not sure why we ever consider leaving any model that's already running
  behind."* `_FLEET_STUDIO` now includes `chat` (named for the GET contract only — verified
  against the whole compiled allowlist, so widening it grants no write), and one explicit work
  entry `POST /studio/chat/v1/chat/completions` was added. The dead-predicate complaint is
  answered from the other side: `_peer_work_request`'s chat branch is live now, and the route that
  was unreachable for every credential that dispatches is reachable. `POST
  /api/hub/chat/completions` is still Hub-token only, deliberately: that is this Mac's own app's
  spelling, and a second spelling for the fleet is the second vocabulary this project keeps
  paying for. Measured cost of the gap, recorded here because the review predicted it as "nothing
  breaks today": `memory_control.SUPPORTED_MODALITIES` already included chat, so a controller's
  memory inventory listed a peer's chat studio and read it as `error` from the 403; it reads
  `ready`. See `docs/tasks/ST-14.md` ST-14.4c and `tests/test_chat_hub_wiring.py`.

### F7 — `activity` accepts the `chat` studio but raises if a chat job is ever reported **[M]** — latent

- **What.** `VALID_STUDIOS` gained `chat`, but `VALID_OPERATIONS`, `_ALLOWED_OPERATIONS` and
  `_DEFAULT_OPERATION` did not. A non-null `active`/`latest` job for studio `chat` hits
  `_DEFAULT_OPERATION[studio]` and `_ALLOWED_OPERATIONS[studio]`.
- **Where.** `components/hub/backend/activity.py:34-44`, used at `:128-129`.
- **How established.** `activity.validate_snapshot({... "studio":"chat", "active":{...job...}},

### F8 — Chat input validation is materially weaker than the Image worker's **[M]**

- **What.** `/v1/chat/completions` converts with bare `float()`/`int()` and validates nothing:
  no bounds or finiteness on `temperature`/`top_p`, no bound on `max_tokens`, no type check on
  `thinking`, no limit on prompt size or message count.
- **Where.** `components/chat/app/backend/main.py:152-154` and `:164`; the engine then does
  `min(int(max_tokens or …), self.max_output_tokens)` (`llm_engine.py:278`). Compare
  `components/image/app/backend/generation.py:35-77`, which pins revision, rejects unknown keys,
  bounds steps/guidance/seed, requires `math.isfinite(guidance)`, caps the prompt at 4,000
  characters and publishes `generation_limits`.
- **How established.** A recording engine behind the real app:

  | request | accepted? | engine received |
  | --- | --- | --- |
  | `max_tokens: -5` | 200 | `max_tokens=-5` |
  | `max_tokens: 0` | 200 | `None` (silently becomes 4,096) |
  | `max_tokens: 1e11` | 200 | `100000000000` (engine caps it) |
  | `temperature: NaN` | 200 | `nan` |
  | `temperature: -3.5` | 200 | `-3.5` |
  | `thinking: "false"` | 200 | `True` |
  | `response_format: 42` | 200 | `42` (silently no JSON mode) |

- **What breaks.** No arbitrary model path, no filesystem path and no unbounded context are
  reachable — the model directory comes only from `STUDIOHUB_MODELS_DIR` + the pinned manifest,
  and the engine caps output at `max_output_tokens` — so this is not a sandbox escape. It is a
  contract gap: a negative temperature inverts the sampler (mlx-lm's `make_sampler` only
  special-cases `temp == 0`, so `-3.5` samples from the *least* likely token), `NaN` reaches
  `mx.random.categorical`, `0` silently means 4,096, and `"false"` turns thinking **on** with no
  field in the response saying so — the exact opposite of the fix the whole task is built around.
  A huge prompt is unbounded work for a 262k-context model.
- **Smallest fix.** One `validate_request()` in the style of the Image worker: reject
  non-finite/out-of-range sampling values, clamp `max_tokens` to `1..max_output_tokens`, require
  `type(thinking) is bool`, cap total prompt characters, and publish the accepted bounds in
  `/api/catalog` (the Image worker publishes `generation_limits`; chat publishes none). Also make
  the catalog's `generation_defaults` match the route: `/api/catalog` advertises `top_p: 0.8`
  (`main.py:128`) while the route defaults to `0.95` (`main.py:154`).

### F9 — Test quality: the native suite is a text search, and the engine tests never exercise the thinking path **[M]**

- **What.** `tests/test_chat_native_wiring.py` (9 tests) reads `StudioAPI.swift`,
  `StudioViews.swift` and `ShellCore.swift` as strings and asserts substrings. It would pass with
  a completely non-functional Chat page.
- **Where.** `tests/test_chat_native_wiring.py:22-74`. The clearest example is
  `test_chat_turns_are_published_state_not_a_local_only_buffer` (`:72-74`), which checks only that
  the *names* `chatPrompt`, `chatTurns`, `submittingChat` appear somewhere in the file — it does
  not check `@Published`, so the property it is named after could be removed and the test still
  passes. `test_send_is_gated_on_a_ready_chat_model` (`:58-65`) searches 700 characters after
  `Button("Send")` for three substrings; an inverted or short-circuited condition still passes.
- **How established.** Read the file and checked what each assertion actually constrains; the
  Hub-side suite by contrast (`tests/test_chat_hub_wiring.py:206-219`) drives a real loopback
  worker and asserts the re-signed token, which is genuine behaviour.
- **What breaks.** ST-14.5's "9 passed" is not evidence that the page works, and the record's
  claim that these tests cover "Send gated on a ready chat model, retired-model reconciliation,
  the Hub route and the wire structs" overstates them. The docstring *is* honest that they "pin
  the source"; the risk is that a reader takes the count as behavioural coverage.
- **Smallest fix.** Move the three checks that matter into the Swift fixture suite
  (`tests/native/api_main.swift`) where a real `NativeWorkspaceStore` runs against the fixture
  protocol: send-with-no-ready-model must not POST, the POST body must carry the selected model,
  and the transcript must survive a refresh. Keep the grep tests only for what cannot be reached.
- **Same family, lower stakes:** `tests/test_chat_worker.py`'s `_FakeTokenizer`/`_StubTokenizer`
  (`:256-265`, `:353-361`) have **no** `enable_thinking` parameter, so the "real engine through the
  real app" tests (`:379-407`) all take the `except TypeError` fallback in `_prompt` and never
  exercise the default-off path. Only `test_thinking_is_off_by_default_and_can_be_requested`
  (`:277-299`) uses a tokenizer that accepts the flag. The production path is therefore covered by
  one narrow test; the integration path is covered by the fallback. Worth one extra stub with the
  real wrapper's signature.

### F10 — The default memory policy unloads the model after every turn **[M]** — observation, not a defect

- **What.** `DEFAULT_MODE = "immediate"` (`components/chat/app/backend/memory_policy.py:20-27`) and
  `immediate` has `idle_seconds: 0`, so the idle thread releases the model within one 5-second
  tick of every completion. Each chat turn therefore pays a cold load — I measured **2.43 s** for
  this snapshot — and the app's first token always follows it.
- **How established.** Read the policy plus my own load timing; the module's own docstring notes
  Chat is "the first local Studio that can hold a text model between jobs", and `immediate` is
  inherited from the Image/voice rationale rather than chosen for chat.
- **What breaks.** Nothing functionally. But it means the numbers in §2 of the qualification
  describe a warm engine that the app's default configuration never has, and a conversation with
  the Studio pays 2.4 s per message. Either default chat to `balanced` or say in the evidence note
  that the app's default is a cold load per turn.
- **Smallest fix.** A one-line default change (or an operator-visible note on the Chat page). No
  code defect.

## 4. What I could not verify, and what would be needed

- **The app itself.** No GUI session was run: I did not open the Chat page and send a message.
  Given F2, it could not have succeeded on this Mac, and the qualification says the same
  ("packaged GUI interaction … is not part of these HTTP-level proofs"). A live run against a
  *corrected* library index is what would close this.
- **A second real-model load.** I loaded the 6 GB snapshot exactly once, ran a plain and a JSON
  completion, recorded memory, and released it (`loaded: false`, active memory 44 bytes). The
  packaged-Hub dispatch proof was therefore not re-taken; I relied on its saved artefacts plus an
  independent engine run.
- **The 0.6.56/`928ebd4` bundle.** It has been replaced by 0.6.58/`eea477e`. Only the runtime
  digest could be confirmed to have survived.
- **The full root suite** (claim 18) — not run; the one known error is a 300-second Voice timeout
  that ST-13 owns.
- **Per-tier throughput (8/16/24 GB).** Unmeasured by the implementer and by me. This is the
  largest genuinely open question in the record, and it is the one that decides whether the
  16 GB fleet can use this model. It needs one timed run per tier, real weights, and the same
  prompt, with the memory policy pinned.
- **Kit `verify-kit.sh` end-to-end.** I verified the libraries (index, digests, bytes) but did not
  execute the script, because it starts a Hub from a removable drive while another agent is
  working on this Mac. The `RESULT: PASS` line itself is unverified.
- **The OptiQ 8.22 GB claim and the upstream gateway/Story contract** — network-dependent, not
  re-fetched. `research/chat-studio-gateway-bridge.md` is a read-only handoff; I did not check
  gateway-kh.
- **The 181-file count** (my count is 182) and the counting rule behind it.
- **A live-socket reproduction of F1/F5.** My reproductions run the real app object under an ASGI
  transport / a real uvicorn server rather than the multi-process packaged Hub. The route code,
  the real manifest catalog and the lease bookkeeping are the production ones; the hotfix commit
  independently reports the same F1 measurement from a live Hub.
- **`stream: true` through the Hub.** I proved the worker-side behaviour with a raw socket and a

## 5. What is genuinely well built

- **The engine's "no invented numbers" posture is real and rare.** Context comes from the model's
  own nested `config.json`; when nothing is published the value is `None` rather than a guess
  (`llm_engine.py:97-116`, with a test that pins it). `release()` refuses while generating instead
  of reporting a release it did not do. Lazy load, one lock, one model.
- **The thinking fix is correct and was verified against the real tokenizer, not a mock.** The
  vocabulary-inferred `has_thinking` default is exactly the trap here (the template's default is
  thinking **on**, so a tokenizer that silently ignores the kwarg would have re-broken JSON mode),
  and the fix survives it. This is the single most valuable technical result in ST-14.
- **The model manifest is exact and internally consistent.** Eleven pinned files, per-file size
  and SHA-256, a 40-hex revision repeated in every URL, an accepted validator row, and — the part
  that matters — the bytes on disk match it to the byte. The catalog test pins the whole release
  menu against it.
- **The packaging path is careful**: `-I -B`, owner-only token file with `O_NOFOLLOW` and mode
  checks, `os.setsid` isolation with parent-PID verification, environment scrubbing, a guarded
  worker spec that refuses an incomplete bundle, and a CLI check that reports the exact runtime
  identity. I ran the *installed bundle's* `chat_worker.py --check` and it reported a coherent
  identity.
- **Some Hub tests test behaviour.** `tests/test_chat_hub_wiring.py` stands up a real loopback
  HTTP worker and asserts the Hub re-signed the request with the worker's own token and forwarded
  to the right path — that is a test that can fail for the right reason. The memory-policy tests
  drive real idle-release timing.
- **The evidence note is honest about its own limits.** It labels the speed comparison as not
  like-for-like, states plainly that per-tier throughput, GUI interaction and independent review
  are missing, and keeps the external GenStudio chat lane deliberately separate rather than
  silently merging two meanings of "chat". Its raw artefacts match its quoted numbers.
- **The F1 fix, once found, was the right shape**: a named mapping with a comment naming the
  failure, a `ValueError` that says which two files must agree, and a regression test that walks
  the *real* catalog — the exact class of test whose absence hid the bug. The tree moved from
  broken to fixed with a proper guard within the review window.
