## Scope

The native shell now persists the editable start-at-login preference with a
backward-compatible default of on, maps the actual `SMAppService` state to
enabled, requires approval, disabled or unavailable, and registers only during
normal first setup or an explicit preference action. Window close keeps the
menu-bar app and its owned service alive. Explicit Quit still terminates and
reaps the owned process group.

An owned service crash or readiness timeout gets a bounded number of automatic
recovery attempts with configurable backoff (default: three attempts at 1/3/10
seconds). The policy is persisted in the existing app preferences and accepts
0–10 attempts and 0–300 second delays; zero disables automatic recovery. Brief ready/crash cycles retain the
bound; the counter resets only after 60 seconds of health or an explicit manual
Start. Stop and Quit cancel a pending recovery task even when no worker process
is currently present. A readiness timeout retains the existing 15-second force-stop
escalation, while an explicit Cancel Recovery action suppresses timeout retry
without resetting the bounded crash count. Recovery requires the selected model directory to remain
available, and never adopts an already-running owner. Readiness and preferences
are read only from owner-readable regular files, with no symlink/FIFO or
group/other-readable acceptance. A missing selected volume remains selected and
unavailable; no replacement model directory is created. Reconnecting after a
restart uses the existing Hub refresh/reconciliation flow, preserving pending
job identities and the Hub's uncertain Voice fencing.

## ST-11 physical procedure

Prerequisites: an original M1 or newer Apple Silicon Mac, a logged-in user,
the candidate Sonoma 14.x point release, a signed or locally approved app
build, an external SSD containing a complete model library, and permission to
use System Settings > General > Login Items. Keep a last-known-good app and
an owner-only test data directory. Do not use this procedure before preserving
the test job/output fixtures.

1. Launch the app while logged in, select the existing SSD library, and record
   the exact app/runtime/model IDs, OS point release, chip, RAM and stable node
   identity. Confirm the library path is retained and no second library is
   created.
2. In Settings, record the initial Start at login state. Enable it, approve it
   in Login Items when macOS requests approval, relaunch, and record the
   resulting `enabled` state. Disable it, relaunch, and record `disabled`.
   If the OS or bundle cannot provide the service, record `unavailable` with
   the macOS error; do not label `requiresApproval` as enabled.
3. Close the main window and verify the menu-bar item remains available and a
   health request still succeeds. Use the menu-bar Quit action and verify the
   Hub, all owned workers, readiness files and worker descriptor are gone.
4. With one short fixture job accepted, pause/drain through the existing owner
   controls before logout. Log out and back in. Verify the same data directory,
   job/item/attempt IDs, settings and model receipts are present; a lost
   response must remain uncertain until reconciled and must never create a
   duplicate generation.
5. Repeat after a normal reboot. Separately disconnect the selected SSD and
   launch: record the explicit unavailable error and verify no replacement
   folder appears. Reconnect the same SSD and use the normal retry/recheck
   flow.
6. Crash an owned child in a disposable fixture, verify the Hub exits or
   recovers only its own service set, and verify no unrelated process or port
   is signalled. Repeat with an occupied Hub port and a missing readiness file.
7. For an OS upgrade, leave generation paused/drained, record the last
   compatible app/runtime, perform the owner-controlled upgrade, and after
   login verify readiness and compatibility before accepting new work. Do not
   claim generation continued through the installation restart.

The software portion of ST-09.OS reuses the existing owner-authenticated Hub
machine control and restart restore path: setting a registered machine's
`enabled` flag to false persists on disk, blocks new admission, and leaves an
active Voice item with its original machine, Studio and worker job ID. Hub
startup calls `broker.restore_batches()` and `transcription_jobs.restore_batches()`;
native reconnect refreshes the existing job identities and keeps uncertain
submissions fenced. Native pause/drain controls remain in the root-owned
ST-08 `StudioAPI.swift` workflow. Physical login/logout/reboot, SSD, OS and
model qualification receipts belong to ST-11.
