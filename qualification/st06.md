is separately owned and separately persisted, reuses the Voice export source at
one tracked location, runs the real pinned Whisper Turbo package offline, and
produces Text/SRT/VTT through its own worker process. It is **not** integrated
into the packaged app yet: that needs shared-file changes the coordinator owns
(listed in [st06-handoff.md](st06-handoff.md)). Base and Small are catalogued and
pinned but **cannot run** on this runtime, for a concrete reason proved below.
No independent review has been done.

## ST-06.1 — decode/export reused at one tracked source location

`components/subtitle/app/backend/engine.py` imports the existing Voice module
`components/voice/app/backend/transcription.py` as `backend.transcription`
(`STUDIOHUB_VOICE_APP_DIR` points at the tracked `components/voice/app`). It calls,
and never copies:

* `segments_to_srt` and `segments_to_vtt` for Text/SRT/VTT export,
* `_normalize_segments` for MLX-Whisper padding-hallucination discard,
* `_audio_duration_seconds` for the media-duration probe.

Proven single source identity:

| Item | Value |
| --- | --- |
| File | `components/voice/app/backend/transcription.py` |
| SHA-256 | `09e8def3c013e5080b5c91927c9b088475f7d65c2206322fbb449c8491e0ff08` |

`one_source_location()` reports this path and digest at runtime, the service
exposes it from `/api/catalog`, and `ExportSourceTests` asserts the loaded module
equals the hash of that one file and that the SRT/VTT output is byte-identical to
a direct call of the Voice functions. `test_no_formatter_is_reimplemented_in_subtitle`
fails if any file under `components/subtitle/` grows its own `-->` cue builder or
a second `segments_to_srt`/`segments_to_vtt`.

The decode call keeps the adopted Voice decision
`condition_on_previous_text=False` (Voice measured 94% fewer invented words) and
is deliberately not caller-configurable.

**Difference from Voice, deliberately:** Voice loads Whisper from its private HF
cache and fetches the tokenizer from an OpenAI repo ID. Subtitle loads the model
from the ST-01 verified package folder and attaches the tokenizer from a
**private verification-checked copy** of the verified companion folder, so
inference never resolves a moving upstream repository. Runtime contract,
"Functions used by ST-02":

> ST-04/ST-06 must pass the verified local companion folder to that existing
> tokenizer path, so runtime inference never resolves a moving upstream
> repository or fetches missing assets.

### Finding and fix: loading must not write into the verified package

An earlier revision attached the tokenizer by loading
`WhisperTokenizer.from_pretrained(<verified package>/companions/processor)`
directly from the model library. Measured effect of one real transcription:
**every file in the verified package** (`model/config.json`,
`model/weights.safetensors`, and all seven `companions/processor/*` files) had
its `ctime` bumped while inode, `mtime`, size and SHA-256 were unchanged. ST-01's
`preflight` then reported
`invalid — File changed; verify again: companions/processor/added_tokens.json`
after every run, so the Subtitle worker invalidated its own model receipt.

The worker no longer loads from the model library. `engine._private_processor`
copies the declared `companions/processor/*` files into
`<subtitle state>/processor/<package>/<revision>/`, re-verifying each copy
against the manifest's `size` and `sha256` first, and the tokenizer loads from
that private copy. Loading a package therefore cannot write into the model
library at all. `SubtitleRealModelTests.test_verified_package_tree_is_never_modified_by_decoding`
is the regression: it fingerprints inode/`mtime`/`ctime`/size for every package
file, runs a real transcription, and asserts the fingerprints and the
`files_verified` state are unchanged. It passes.

This is a **contract-relevant finding for the coordinator**: any worker that
loads a shared artifact in place from a verified package must either stage a
private copy or expect ST-01's receipt to flip to `invalid` on real use. The
shipped Voice runtime is immutable, but the model library is not.

## ST-06.2 — independent process, cancellation, history

`components/subtitle/` is a private FastAPI service with its own state:

| Surface | Path |
| --- | --- |
| Health | `GET /api/health` |
| Catalog | `GET /api/catalog` |
| Voice-compatible STT availability | `GET /api/transcribe/availability` |
| Voice-compatible synchronous STT | `POST /api/transcribe` (multipart) |
| Submit | `POST /api/generate/transcribe` |
| History / status | `GET /api/generate/transcribe/jobs[/{id}]` |
| Cancel | `DELETE /api/generate/transcribe/jobs/{id}` |
| Artifact | `GET /api/generate/transcribe/jobs/{id}/artifact?format=srt\|vtt\|text` |
| Verified receipt | `POST /api/generate/transcribe/jobs/{id}/ack` |

State separation is structural, not a separate tab: its own `jobs.json` ledger,
its own `inputs/` and `artifacts/` trees under `<data>/subtitle/`, its own loopback
port and process group, its own owner-token middleware. The owner worker is
`packaging/subtitle_worker.py`, run with immutable Python `-I -B`.

Cancellation is cooperative at the boundaries this mlx-audio release permits:
before the model load and immediately after decoding. A cancel during decoding
still discards the result and publishes no artifact. This limit is stated rather
than hidden. Restart behaviour mirrors the Image worker: a queued/running job
becomes `WORKER_RESTART_UNCERTAIN`, existing artifacts without a durable receipt
become `JOB_PERSISTENCE_UNCERTAIN`, and a completed job whose artifact no longer
matches its recorded size/hash becomes `OUTPUT_UNAVAILABLE`.

Public Subtitle state is separate; immutable assets are shared. The service uses
the bundled Voice runtime (which already contains `mlx-audio`) and the shipped
model manifests. `packaging/stage_voice.py` would ship the same runtime tree for
both, and the release manifest records the shared runtime identity under
`components.subtitle.runtime_sha256`.

### Base and Small cannot run — exact blocker

**(a) What kind of limitation it is: an mlx-audio loader limitation, not a
packaging mistake by ST-01.** The manifest correctly pins what the upstream
`mlx-community/whisper-base-mlx` and `whisper-small-mlx` repositories actually
publish at those revisions — HF metadata confirms both ship only `weights.npz`
(Base revision `1e3e249f…`, Small revision `45f39159…`). The bundled
`mlx_audio` Whisper loader reads only `*.safetensors`:

`.build/voice-runtime/lib/python3.12/site-packages/mlx_audio/stt/models/whisper/whisper.py:665`
`wf = glob.glob(str(model_path / "*.safetensors"))`

so it loads an **empty weight dict** and returns a randomly-initialised model.
This is not introduced by the adopted Voice code: Voice calls the same
`mlx_audio.stt.utils.load_model`, and Voice's registry only ever named
safetensors variants, so Voice never hit it.

The failure is silent and dangerous, which is why the service refuses it:
`load_model(..., strict=False)` is the default, the weight dict is empty rather
than incomplete, and there is no post-load check that any weight was applied. A
naive fix that simply allowed the load would emit fluent-looking garbage. The
service therefore reports `state = unsupported_weight_format`,
`runtime_supported = false`, not ready, and returns `409` on submit.
`test_npz_only_packages_are_reported_not_runnable` and
`test_submitting_a_non_runnable_package_is_refused` cover this.

**(b) Runnable paths exist — three of them, none attempted here:**

1. **Offline conversion with the bundled tooling (recommended).** The Voice
   runtime already contains `mlx_audio.convert.convert`, whose general
   dequantize/convert flow loads weights with `load_weights`/`mx.load` (which
   handles `.npz`) and writes `model.safetensors`. A build-side step would
   convert the ST-01 pinned npz folder into a new project-managed
   revision, then pin that revision in the manifest. This keeps the pin
   deterministic and adds no network dependency at node runtime. It needs a
   new checksum and a real transcription check before it is claimed.
2. **Pin upstream PyTorch safetensors instead.** `openai/whisper-base`
   (`model.safetensors`, revision `e37978b9…`) and `openai/whisper-small`
   (`model.safetensors`, revision `973afd24…`) both publish safetensors at the
   exact revisions ST-01 already uses for their processor companions. The
   loader's config/quantization path handles HuggingFace-format weights, so this
   may load directly — but it would need verification (and Whisper has no
   quantization metadata in those repos).
3. **Add a narrow `npz` read path** to the runtime's Whisper loader. Smallest
   code change, largest blast radius: it edits the vendored, audited runtime,
   which means re-auditing and re-hashing the runtime tree.

**(c) Recommendation:** treat this as its own checkpoint (a
"ST-06.BASE-SMALL" or shared runtime/model-package task) and do option 1 —
build-side conversion to `safetensors`, repin the revision, update the manifest
digest and file checksums, and require a real Base and Small transcription
before either is advertised. Option 2 is worth a quick test first because it is
cheaper, but it must be verified rather than assumed: a wrong load here is
silent. Do **not** relax the refusal gate without one of these; the current
behaviour is the honest one. Until then Base and Small stay catalogued and
non-runnable, and Turbo alone satisfies the real Whisper evidence.

## ST-06.5 — input, failures, exports, originals

* Input types accepted match the Hub's existing list: `.wav .mp3 .m4a .aac .flac
  .ogg .opus .webm .mp4 .mov`. A foreign extension is refused `422`
  (`test_hub_transcription_rejects_a_foreign_extension`).
* The original upload is preserved: it is stored under
  `<data>/subtitle/inputs/<label>-<id>/original<ext>` at mode `0600` and only
  copied/decoded from; nothing in the Subtitle service deletes or rewrites it.
* Failures are classified, not flattened: `INPUT_NOT_FOUND`,
  `MODEL_FILES_UNAVAILABLE`, `INVALID_SUBTITLE_REQUEST`,
  `TRANSCRIPTION_UNAVAILABLE`, `TRANSCRIPTION_FAILED`, plus the two persistence
  codes and `OUTPUT_UNAVAILABLE`.
* Exports are Text, SRT and VTT, each published atomically with recorded bytes
  and SHA-256; a partial cue file is never published.
* Only implemented timestamp controls are exposed: `word_timestamps` (the real
  mlx-audio Whisper option) plus language. No invented subtitle timing options
  are advertised.

### Not proven for Turbo

* Video-container input (`.mp4`/`.mov`) end to end — accepted by the guard but

## ST-06.6 / ST-06.2 — what is NOT proven

* **Not integrated into the packaged app.** `packaging/hub_worker.py` does not
  start a Subtitle child yet, the release manifest has no
  `components.subtitle`, and `packaging/stage_voice.py` does not ship the tree or
  worker. No assembled-app Subtitle receipt exists.
* **No native UI path.** The native Transcription workspace still calls
  `/studio/voice/api/transcribe/availability` and
  `/api/hub/transcription/jobs`; there are no `/studio/subtitle/api/...` routes.
* **No real CLI/native end-to-end lifecycle**, restart or cancel through the
  packaged app. Lifecycle proof is at the manager/API/worker level.
* **No Base/Small inference** (blocked above) and therefore no per-model
  restart/cancel/history check.
* **No node-concurrency proof** (multiple Subtitle workers on one machine/fleet).
* **No independent review** of this work.

## Remaining limitations

1. No packaged-app integration (shared-file changes listed in the handoff).
